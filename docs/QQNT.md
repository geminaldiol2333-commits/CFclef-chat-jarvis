# QQ NT（Windows）适配调研

> **状态：未实现。** 本文只记录调研、实测数据和阻塞点，代码里还没有 QQ 适配器；
> `app/chatapps.py` 目前只有微信。等真要做的时候按这里走，不用重新摸一遍。

## 结论摘要

1. **上游和所有 fork 都没有 QQ NT 支持。** 查过 `jev-chat/jev-chat-windows` 全部 11 个近期有提交的
   fork，`app/chatapps.py` 里一个 QQ 都没有；上游自己明确只维护微信这一套识别。
2. **QQ NT 不是「`chatapps.py` 加一行」就能好的。** 窗口目标很好认（一行就够），难点是
   **消息区 / 输入框定位**：本项目的 `chat_area()` 靠「面板底色 = 画面里最常见的颜色」做像素锚点，
   而 QQ NT 的聊天区是**壁纸 / 渐变**而不是平底色，锚点直接失效（实测返回整个窗口）。
3. **气泡颜色随主题变。** 本机实测的那套主题是改过的（见下表），所以「自己的气泡」不能写死一个色值；
   要么按主题标定，要么做成可配置项。
4. 顺带一提：Android 版（`Finderchangchang/jev-chat-JARVIS`）**是支持 QQ 的**（读无障碍节点，
   9.3.50 实测）。判断口径和题目集跟本项目共用，所以「QQ 场景该问什么、怎么判」这部分不用重新设计，
   缺的只是 Windows/QQ NT 这一侧的采集适配。

## 本机实测数据

环境：QQ NT `9.9.36-53644`（同时装了 `9.9.31-49738`），Windows，系统缩放 125%，
主题/气泡是用户改过的（非默认）。测量方式：只抓像素统计颜色，**不跑 OCR、不读文本、不落盘**。

| 项 | 实测值 |
| --- | --- |
| 顶层窗口类名 | `Chrome_WidgetWin_1`（Electron / Chromium） |
| 主窗口标题 | 恰好 `QQ`（`title == "QQ"` 可直接用于 `main_title`） |
| 可见顶层窗口数 | 1 个（默认把聊天区嵌在主窗口里，没有独立聊天窗口） |
| 窗口矩形 / 抓到的帧 | `1328x768` → 帧 `1660x960`（125% 缩放，帧是物理像素） |
| 自己的气泡底色 | ≈ `rgb(0,128,245)` = `#0080F5`（品牌蓝） |
| 聊天区背景 | ≈ `#D5E2F6`（浅蓝壁纸，**不是平底色**） |
| 对方气泡（该主题下） | 白色 `#FFFFFF` / 粉 `rgb(253,217,218)` |

### 建议的颜色规则

实测背景 `#D5E2F6` 离「蓝」其实不远，宽松规则（`b > r + 40 and b >= g + 20`）在别的主题下
有可能把背景也算成自己的气泡。用**高蓝低红**更稳：

```python
def _qq_me(bg):
    r, g, b = int(bg[0]), int(bg[1]), int(bg[2])
    # QQ NT 自己的气泡是品牌蓝（实测 #0080F5 一类）。
    # 聊天区壁纸实测约 #D5E2F6，红通道很高，靠 r < 120 挡掉。
    return b > 180 and r < 120 and b > r + 120 and b >= g + 30
```

对下列颜色成立 / 不成立（做单元测试时用得上）：

| 颜色 | 判定 | 说明 |
| --- | --- | --- |
| `#0080F5` `(0,128,245)` | ✅ me | 本机实测的自己的气泡 |
| `#12B7F5` `(18,183,245)` | ✅ me | 旧版 QQ 蓝 |
| `#4A9EFF` `(74,158,255)` | ✅ me | 常见 QQ 蓝 |
| `#D5E2F6` `(213,226,246)` | ❌ | 聊天区壁纸（`r` 太高） |
| `#FFFFFF` | ❌ | 对方气泡 / 面板 |
| `rgb(253,217,218)` | ❌ | 本机主题里的粉色气泡 |
| 微信绿 `(149,236,105)` | ❌ | 与微信规则互不误伤 |

## 为什么 `chat_area()` 在 QQ NT 上失效

`app/capture.py::chat_area()` 的做法：

1. 取右半边抽样，算**最常见颜色**当面板底色 `bg`；
2. `isbg = |像素 - bg| <= 6`，按列求 `isbg` 占比；第一根占比 > 0.3 的列 = 面板左边界 `x0`，
   最后一根 = 右边界 `x1`；
3. 按行同理求面板上下边界；再用「整行单色且非底色」找横向分隔线，分隔线里 45% 高度以下
   第一根当作**输入框顶** `y_in`；
4. 面板顶部 + `header_h` 当作消息区顶 `y_top`。

QQ NT 的聊天区是壁纸 / 渐变，**没有任何一种颜色占比高**，于是：

- `isbg` 掩码几乎全空 → 列的占比永远到不了 0.3 → `np.argmax` 返回 `0` → `x0 = 0`、`x1 = W`；
- 同样找不到分隔线 → `y_in = H`、`y_top = y_pane + 60`。

实测输出正好是这个退化结果：

```
chat_area() -> (0, 60, 1660, 960)     # x0=0, y_top=60, x1=1660(=W), y_in=960(=H)
```

后果：OCR 会把**会话列表、搜索框、标题栏**一起读进去；`fill()` 会点在
`(x0+60, y_in+40)`，也就是窗口右下角，而不是输入框。**所以光加 `chatapps.py` 条目是没用的。**

## 要真正落地需要三件事

1. **窗口目标**（容易，已确定）：`exes = ("qq.exe",)`、`main_title = "QQ"`。
   若用户把会话拖成独立窗口，再把联系人名标题加进 `skip_titles` / 另做分支。
2. **面板与输入框定位器**（难点）：换成不依赖平底色的算法。候选做法：
   - 找**竖向分界线**：会话列表和聊天区之间有一条可见的竖直边界，取左三分之一内
     列间色差最大的那一列当 `x0`；
   - 输入框是底部一块**浅色圆角矩形**（有边框），按底部区域的横向长边缘找 `y_in`；
   - 或者直接按 QQ NT 的固定布局比例估（风险高：DPI、缩放、主题都会变）。
3. **颜色规则**：用上面那条高蓝低红规则，并考虑做成 `config.json` 可配（因为主题可换）。

### 两条路线

| | 像素 + OCR（沿用现有架构） | UIA（无障碍节点） |
| --- | --- | --- |
| 前提 | 无 | QQ 必须用 `--force-renderer-accessibility` 启动 |
| 自己/对方、发言人名 | 靠颜色 + 位置猜 | 节点里直接有，准确 |
| 工作量 | 中（要新写定位器 + 调参） | 大（多一套采集路径，等于 Android 版那套搬过来） |
| 脆弱点 | 主题、壁纸、DPI | QQ 大版本更新后节点结构可能变 |
| 合规 | 与现在一致（只截图） | 也符合「不注入」，但要改启动方式 |

## 怎么验证 / 怎么调

仓库里留了两个探针（都只读像素、不打印文本、不落盘）：

```bat
:: 1) 确认窗口类名和标题（决定 main_title 怎么填）
python probe\probe_qq_windows.py

:: 2) 看 chat_area() 认出了什么、聊天区实际配色是多少（决定颜色规则）
python probe\probe_qq_pane.py
```

再配合设置页的「调试视图」（绿 = 我、蓝 = 对方、灰 = 过滤掉的灰字、红 = 当成图片丢掉），
能直接看出定位器和颜色规则错在哪一步。

## 注意事项

- **QQ 必须打开、不能最小化**（和微信一样，Windows 不渲染最小化的窗口）。
- **帧是物理像素**，`chat_area(header_h=60)` 的 `header_h` 是按 100% DPI 给的，125% 缩放要按比例放大。
- **不要走 LiteLoaderQQNT 插件那条路**：那是往 QQ 里注入代码，违反本项目「不 hook、不注入、
  不碰对方进程」的硬约束。UIA 和截图都不属于注入。
- QQ 更新（尤其大版本）后窗口结构、配色、DPI 行为都可能变，适配器要能容错并在认不出时
  明确报错，而不是把整个窗口当消息区。
